## 一、這是什麼

EscapeBot 是一個由大型語言模型（LLM）即時驅動的中文密室逃脫遊戲。玩家進入一個由 LLM 生成的房間，透過與遊戲互動（探索、解謎、移動）一步步找到逃脫的方法。

跟傳統文字冒險遊戲最大的不同：**場景、物品、謎題、敘述全部由 LLM 即時生成與回應**，不是預先寫死的劇本。每一場遊戲的房間都不一樣，玩家的任何輸入 LLM 都會即時理解並回應。

### 起源
這個概念最早是作者高中時期的興趣作品（用狀態機 + JSON 寫死的版本）。2026 年 LLM 成熟後重新復活——LLM 讓「即時生成關卡、自由理解玩家輸入」這件當年做不到的事成為可能，於是重做成現在的 LLM 版本。

### 兩個版本
- **Discord 版**（`EscapeBot`，production）：純文字介面，玩家打指令、bot 回敘述。已上線運作。
- **Web 版**（`escapebot-web`，Phase 2）：TypeScript 重寫，部署在 Vercel。這是目前主力開發、重新想像玩法的版本。

兩個版本**共用同一個 engine**（關卡生成、回合處理、規則驗證），只是呈現層不同。

### 名字
- **英文名（已定）：Cat Got Your Words** — 玩英文俗語 *cat got your tongue?*，貼合「貓吃掉你的話」的核心、溫和神秘、好傳。可直接當主名。
- **中文名：未定**（`EscapeBot` 是開發代號/Discord 版名，不是最終對外中文名）。方向偏「貓 + 話/字 + 機靈雙關」（呼應英文名的調性），非「肉包子打貓」那種荒謬畫面路線。

## 二、遊戲目標（產品層）

### 核心成功指標：值得分享
這個專案的成功定義是——**玩家玩完會想主動把它傳出去**：自願截圖、傳連結給朋友、甚至自己帶新玩家進來。這本質上就是 **viral**：讓作品傳播給更多人。衡量的訊號是 organic referral——有人**不是被作者邀請**就自己拉新人進來（Phase 1 已出現過一次，視為達到「值得分享」的最低門檻；要 3-5 個獨立 referral 才能算真正的 traction）。

需要釐清一個常見的誤解：**「值得分享」不等於跟留存對立**。viral 跟回流本來就常常一起發生（分享把人帶進來、玩家回流、敘事 hook 讓人想看下一章）——這些都是追求的。真正被排除的，只是**機械式的留存獎勵**：每日簽到、連續登入、streak、徽章、進度條焦慮這類「把同一個人硬黏回來」的設計。它們靠的是義務感和損失厭惡，而不是作品本身夠好。

這個定位決定了設計取捨：
- **不做**機械式留存獎勵（簽到 / streak / 徽章 / 進度條焦慮）——回流要來自「東西好到想再玩、想看下一段」，不是來自打卡壓力。
- **要做**值得分享的瞬間：一場有趣的遊戲體驗、一個荒謬可愛的畫面、一句難忘的敘述——讓玩家主動想截圖、傳連結給朋友。這是 viral 的核心 unit。

## 三、玩法

### Discord 版（傳統）
玩家打字下指令（移動、查看、解謎），bot 用文字回應敘述。標準的文字冒險互動。

### Web 版（Phase 2 的重新想像）—— 核心爆點

Web 版沒有把 Discord 版直接「加上圖形介面」，而是**根本性地重新想像了「跟 LLM 對話」這件事**。

**核心概念：把「玩家輸入 → LLM 處理 → LLM 回覆」的整個循環，物理化成「餵一隻貓」。**

貓 = LLM 的擬人化身。整個循環變成：

```
1. 玩家打字 + 按「捏」  →  文字捏成一顆包子
2. 拉彈弓瞄準，把包子射向貓（憤怒鳥式）
3. 貓吃掉包子、咀嚼  =  LLM 正在處理輸入
4. 貓吐出一顆包子，落到地上  =  LLM 的回覆
5. 點地上的包子  →  讀到 LLM 的回應內容
6. 包子散落滿地（每顆是一則對話/線索），最新的有描邊標示
```

**為什麼這是爆點：**
- 沒有人這樣做過——把跟 AI 的對話變成餵食一隻會吃會吐的貓。
- 詭異、可愛、有荒謬感——正中「值得分享」的目標（會讓人想截圖：「你看這什麼鬼東西」）。
- 巧妙地解決了 LLM 的延遲問題——「貓咀嚼」的動畫剛好掩護 LLM 處理的 3-6 秒，等待變成有趣的過程而非乾等。
- 「散落滿地的包子」= 散落的對話/線索，玩家撿拾閱讀，把「讀文字」變成「在空間裡撿東西」的體感。

### 包子的分類（規劃中）
包子依內容性質有不同視覺：
- 普通包 = 一般回覆
- 黃金包 = 跟線索相關
- 腐爛包 = weird moment（LLM 對荒謬輸入的詭異回應）

### 操作分流設計
不是所有操作都用「餵貓」——那樣會太繁瑣。不同操作各得其所：

| 操作類型 | 互動方式 | 理由 |
|---------|---------|------|
| 解謎、對話 | 捏包子餵貓 | 適合儀式感，是核心爆點 |
| 查看物品 | 輸入建議（prefill）→ 點選 → 餵貓 | 物品就在眼前，點建議不用想不用打 |
| 移動、換房間 | 建築平面圖點地點 | 空間關係一目了然，點一下就走 |

核心原則：**高頻、輕量的操作（查看、移動）簡化掉，把「餵貓」的儀式感保留給最值得的核心互動（解謎、對話）。**

## 三點五、貓的聲音 / persona（G-catvoice ✅ 已拍板 2026-06-02）

> 全文定稿在 code（turnHandler 的 `NARRATION_SYSTEM_PROMPT`，Phase4），**以 code 為準，本段只記決策脈絡,不複述全文**（免兩邊漂移）。

**聲音定案：認真但奇怪的世界代理人。** 貓是玩家與這個世界之間的中介（LLM 化身）——玩家把想做的事捏成包子交給貓,貓認真去跟世界交涉、誠實回報結果。擬人化一切（門不肯商量、房間把要求記下來）、誠實、偶爾一絲乾、不毒舌不說教、稱呼「你」、簡短。

**為什麼是這個聲音（不是毒舌/別的）**：從核心概念「貓 = LLM 化身」往回推最自洽——它真的在「處理輸入、回報結果」,就像 LLM 在做的事。毒舌會讓貓變成「有脾氣的 NPC」、偏離化身定位,且毒舌易把線索講錯破壞可解性。三方判斷（文件傾向 / Claude 分析 / ChatGPT）都指向「認真但奇怪」。

**接入位置**：只進 Phase4 `generateNarration`（貓人格只在「寫 narration」這拍用）。**不進 Phase1 intent**（純功能）、**不進 Phase2 judge**（中性判定,加人格干擾準度）。

**硬約束（凌駕語氣,接 engine）**：① **state 是底線**——每句描述必須能被 engine 已定 state 直接驗證或反駁;禁止顯性假變化（鑰匙消失/門開）也禁止隱性 drift（模糊措辭/語氣暗示/未明說變更,如「門縫好像動了一下」）。weird moment 最易踩,特別克制,寧可說「沒有變化」。與 acknowledgedOutcomes 是**雙重防線**（persona prompt 壓 + 結構核查）,persona 不取代核查。② 不碰線索/不腦補（接修2）。③ 不宣告勝利（Ending Restraint）。④ 只描述已發生結果。

**examples 教精神、不鎖句式**：persona 裡的情境範例標明 illustrative only,LLM 每次即興抓調性,不照抄句子。

**實玩驗過（2026-06-02）**：7s/回合正常、judge wrong 正確、貓味在（第一人稱、擬人化、誠實）、weird moment 守 state（吃備忘錄「太粗糙吐出來、還在原地」,不撒謊）。

**待微調（語氣小問題,記監測、非壞,多玩確認常態才調）**：
- **weird moment 偶退回第三人稱旁白**：玩家對自己/物品做的怪事（吃東西）時,貓有時退成「你含了一下……」純旁白,丟失第一人稱「我（貓）」的在場感。正常動作（查看/拿取/解謎）貓味穩。
- **句尾句型復讀**：查看/拿取結尾常是「它（不）想告訴我們更多」反覆。examples 副作用,LLM 抓到順的句尾就重複。

**未來監測點（ChatGPT 提,現在不動,未來監測 / 調節）**：
1. **weird moment 的 implicit drift 是最大風險,prompt 堵不死**（= 四拍殘留細縫）。「門縫好像變亮/鑰匙感覺變輕」這種語意鑽洞,acknowledgedOutcomes（抓顯性假成功）抓不到。靠 persona prompt 壓 + 實玩抓,集中在 weird moment。
2. **multi-step puzzle reasoning 時貓會「補合理性」**：這隻會詮釋的貓,未來做多步推理謎題時可能腦補 state 沒有的因果。做 multi-step 時要警惕（接硬約束②不腦補）。
3. **「不提示謎題」≠「不能幫助理解」是調節旋鈕**：現在嚴格封口是對的（先嚴防洩題）。未來若嫌遊戲太卡,可只放寬「貓能多陳述 state 事實/環境」這一條,不用重寫 persona。

## 四、視覺風格

**北極星：順眼 + LLM 擬人化**

- 不追求華麗或複雜的美術，「看起來順眼」即可。
- 採 pixel art（像素風），暖色調（溫馨，配合療癒系的包子與貓）。
- 核心是「貓作為 LLM 化身」這個概念要立得住——貓吃進包子、吐出包子，視覺上就是「LLM 在運作」。
- 場景目前是程式生成的簡單背景（漸層天空 + 暖土色地面 + 接地陰影），之後由設計師用手繪素材替換。

### 主題適配（規劃）
包子作為「對話的物理化身」，其主題可隨遊戲世界觀變化。目前是療癒系（叉燒包），未來不同主題的遊戲可以有不同的「對話物件」。

## 五、技術架構

### Engine（兩版共用）
核心是一套 LLM 驅動的關卡引擎：
- **關卡生成器（scenarioGenerator）**：LLM 生成一整個密室——房間、物品、謎題、出口、通關條件。
- **回合處理（turnHandler）**：玩家每次輸入，LLM 理解並回應，產生敘述 + 世界狀態的改變。
- **規則驗證（ruleEnforcer）**：強制 LLM 的輸出符合遊戲規則（不能穿越未解鎖的門、不能拿不存在的東西等）。
- **世界狀態（WorldState）**：房間、物品、謎題、玩家位置、歷史記錄的完整狀態。

### 核心技術哲學：LLM 的輸出永遠不被信任為最終狀態
這是 EscapeBot 可能的核心技術護城河。LLM 生成的關卡可能不一致、不可解、邏輯有漏洞。所以有一層**生成後的驗證與修復機制**：
- **validateScenarioLogic**：檢查關卡是否有死鎖（例如解鎖某房間的鑰匙被鎖在那個房間裡）。
- **repairItemConsistency**：自動修復可修復的不一致（例如物品的雙向記錄沒對齊）。
- 哲學：**能自動修的就修，真正的死鎖才重新生成。** LLM 的創意產出 + 程式的可靠性保證，兩者結合。

### Web 版技術棧
- Next.js + TypeScript，部署 Vercel
- PixiJS（canvas 渲染貓、包子、場景；用固定透視相機把 3D 世界座標投影成螢幕座標，近大遠小）
- 投擲是真 3D 拋體（解析式 analytic，包子有世界座標 x/y/z，從前景彈弓飛向遠處的貓）
- matter.js（落地後的包子在地面 XZ 平面自然散落堆疊用；飛行不經 matter.js）
- Clerk（登入）、Neon（Postgres）、Drizzle（ORM）
- 架構：PixiJS canvas（視覺互動）+ HTML input（打字，支援中文輸入法）混合

## 七、未來規劃

### 整體路線：三個階段

EscapeBot 的演進分三個階段，差別在於**改變的層次**：

```
Phase 1：文字          — Discord 純文字版，已上線
Phase 2：網頁 + 互動重新想像 — 進行中（改呈現層與互動，底層 engine 不變）
Phase 3：因果圖當底層   — 未來（改底層邏輯模型本身）
```

**關鍵區別：**
- **Phase 1 → 2** 改的是**呈現層與互動**——把文字版變成網頁，重新想像玩家怎麼看、怎麼操作（餵貓、平面圖、prefill）。底層的 engine、謎題生成方式不變。
- **Phase 2 → 3** 改的是**底層邏輯模型**——把現在的 engine 換成以因果圖為底層的架構。這不是介面改變，是遊戲底層怎麼運作的躍進。

這個區別解釋了「為什麼有些問題現在只能止血」：像謎題可解性這種根本問題，治本需要 Phase 3 的因果圖底層，Phase 2 只能輕量處理、撐著。

### Phase 3（未來）—— 因果圖當底層

把遊戲的底層邏輯模型，從現在的 engine 換成**以因果圖為底層**的架構。這是底層的躍進，不是介面改變。

**核心想法：把謎題形式化成因果圖。**
- 線索 = 節點，推導 = 邊，答案 = 目標節點
- 謎題可解 = 答案節點從線索節點**可達**
- 不劇透 = 從線索到答案的**最短路徑 ≥ 2**（需要推導，不是一步直達）
- LLM 不再生成自由文字謎題，而是生成**結構化的謎題圖（描述語言）**，程式驗證這個圖的可達性與路徑長度

**為什麼這能徹底解決謎題可解性：**
- 現在的問題（線索不足、LLM 腦補外部知識）本質上是「答案需要圖裡不存在的邊」。
- 一旦謎題是可驗證的因果圖結構，可解性就是程式能算的（圖可達性），不再靠 LLM 自覺保證。
- 這呼應 engine 既有哲學「LLM 創意 + 程式驗證」——只是把驗證能力從「死鎖」擴展到「完整可解性」。有了描述語言這個結構約束，LLM 生成謎題圖比生成自由文字可靠得多。

**思路來源**：因果圖 / 可達性的設計思路，可參考作者另一個研究專案（因果級聯引擎）的對應 pattern。但 EscapeBot 的實作是自己的（不共用程式碼），只借觀念。

### 長期方向（產品成熟後）—— UGC / 付費 host 平台

更遠的方向：產品成熟、核心玩法被驗證好玩 + 值得分享之後，**開放資源給付費 host，讓他們設計自己的謎題、場景、機制，以及貓的個性**。EscapeBot 從「一個作者做的解謎遊戲」演進成「一個讓別人也能造解謎世界的平台」——作者從內容作者轉成工具/平台提供者，付費 host 產出內容。

這個方向**抬高了某些現有項的長期價值**（解釋了為什麼它們值得投資，即使近程 viral 槓桿不是最高）：
- **Phase 3 因果圖** 不只是作者的護城河，是**給 host 的「可解性保證工具」**——host 不可能手動驗證自己設計的謎題可解，因果圖的可達性檢查能幫他們（或系統）保證。
- **場景 generator / 辨識度** 從「自動生成」延伸成**「能吃 host 設計輸入的創作底層」**（host 給主題/機制/約束，系統生成或半生成有 identity 的場景）。
- **貓人格** 從「定一個固定聲音」延伸成**「一個可被參數化、讓 host 調的維度」**——要設計的不是「貓是誰」，是「貓的人格怎麼被設定」。

**重要界線：這是「成熟後」的方向，不進近程排序。** 早期要驗證的是核心玩法的 viral 與留存（見缺口分析的兩軸）——沒人會想 host 一個還沒被證明好玩的東西。所以平台能力（host 工具、人格參數化、謎題編輯器）是**那個驗證通過之後**才做，現在不該為它提前投入。它影響的是「為什麼做因果圖/generator/人格」的長期理由，不是「現在先做什麼」。

#### 發現 / 分享層：blog 形式（補充）

UGC 平台還缺一層「內容怎麼被看見、被逛」。一個方向是 **blog 形式**——一個可逛、可分享單篇、會累積的內容流。每一篇有自己的 URL、能單獨傳、能被轉，跟現在的 `/s/{shareId}`（單局分享卡）是同一個基因，只是從「一張卡」長成「一篇可逛的內容」。天然為「值得分享」這個北極星服務。

四種內容單元（性質差很多）：
- **有趣場景 / 畫風**：展示型（作品集 / 靈感庫，偏靜態美術）。
- **貓的回應**：金句 / 名場面型。**最接近 viral 核心**（可轉述的句子），最輕、最容易累積——玩家玩的過程本來就在產生貓的對話，只要讓特別好的那幾句能 po 出來、被逛。是 C 版分享卡的自然延伸（從「我存一張卡」→「這些卡匯集成可逛的流」）。**四種裡最早能驗證、幾乎免費的形態。**
- **謎題挑戰**：可玩型——別人能點進去玩同一關。= replay + UGC 關卡的合體，最有黏性也**最重**（要 replay + host 關卡 + 可解性保證 → 指回 Phase 3 因果圖）。展示型可以早，可玩型要等 Phase 3。
- **贊助商場景**：商業模式，不是內容類型。品牌出錢做客製/聯名場景公開曝光。與付費 host 是同一條商業線的兩種形態（host 付費造私房內容 vs 贊助商付費造公開曝光內容）。

**待定（定性問題）**：這個 blog 是**官方策展**（你/系統挑精選 po 出來，像 showcase，輕、可控品質）還是 **UGC 內容流**（host/玩家自己發布，像 mini 社群，重、要審核/排序/防濫用）？「贊助商場景」偏策展，「玩家分享貓回應」偏 UGC。方向未定。

**同屬「成熟後」長期線，不進近程。** 但它反過來提醒近程：現在做分享卡（M4a / C 版）時，資料結構與 URL 結構可以**往「未來會長成可逛內容流」的方向留餘地**，避免之後重做。

## 八、設計哲學總結

1. **為「值得分享」設計，也就是為 viral 設計**——做讓人想主動傳出去、想帶人來玩的東西。不靠機械式留存獎勵（簽到 / streak / 徽章）把同一個人硬黏回來，但 viral 帶來的傳播與回流是追求的。
2. **根本性地重新想像，而非加層**——Web 版不是 Discord 版 + GUI，而是把「跟 AI 對話」重新想像成餵貓。
3. **LLM 的創意 + 程式的可靠性**——LLM 生成關卡，但程式驗證並保證它可解、一致。LLM 輸出永不被信任為最終狀態。
4. **把限制變成特色**——LLM 的延遲，用「貓咀嚼」的動畫掩護成有趣的過程。
5. **操作分流，各得其所**——把儀式感留給核心互動，高頻操作簡化。
6. **順眼即可，概念立得住最重要**——視覺不追求華麗，但「貓 = LLM 化身」這個核心概念要清楚。
