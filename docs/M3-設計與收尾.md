> 包子貓循環 + 貓 LLM 化身。**M3 已上線**，投擲後續改成真 3D 深度鎖定。

## 🆕 3D 縱深改造（最新狀態）

M3 上線後，把投擲從「2D 側視 + 假縱深縮放」整個改成**真 3D 深度鎖定**，解掉早期「包子直上直下、原地縮小、看起來假」的問題。

- **真透視投影**：固定相機把 3D 世界座標 (x,y,z) 投影成螢幕座標，近大遠小自動成立（取代手刻的 depthOf/perspScale）。彈弓在前景、貓在遠處，包子真的往畫面深處飛向貓、一路縮小。
- **深度鎖定**：貓固定在一個深度平面；包子的深度速度自動求解，使其在到達貓高度的同一刻到達貓的深度 → 深度永遠不會失手。玩家只瞄**左右 + 力道**，深度系統包辦——把「平面螢幕上瞄深度」這個最難的問題從根繞掉。力道不足（弧頂搆不到貓高度）→ 判短少、彈回。
- **飛行純 analytic 3D**（不經 matter.js）；**命中改 3D 距離判定**（球形，取代 sensor body + 碰撞事件）。
- **落地散落**：包子落地後在地面 XZ 平面用 matter.js 自然散開（gravity 關掉，靠初速 + friction），近大遠小由投影決定。
- **場景**：全寬地面（取代早期梯形/窄地面），縱深靠真投影 + 貓遠小撐。彈弓前景置中、貓遠處置中（用實測 PNG 內容中心對齊，非 sprite 框）。

驗收（實玩）：不假、shoot 手感好、命中度好、狀態都接上。

## ✅ 早期完成（M3.1b + M3.2 核心，3D 改造前）

從一張貓草圖到能玩通一場的完整爆點：

- **核心循環接真 engine**：捏包子(打字+捏)→ 拉彈弓瞄準 → 命中貓 → 貓吃/嚼/吐(= 真 submitAction，LLM 處理)→ 回覆包子落地 → 點選撿讀真 narration。全程接真 engine，能玩到通關 + 接上分享卡。
- **憤怒鳥式拖曳瞄準**：拉彈弓(往後拉定方向+力道)、橡皮筋視覺、軌跡預測(解析公式，跟物理一致)、命中時貓高亮、能丟歪要練瞄準。
- **物理 / 散落**：回覆包子落地自然散開堆積、互不重疊(治本，取代固定 slot)。滿地包子是設計的一部分(不清理)。（註：飛行與命中的物理在 3D 改造後已改為 analytic + 3D 距離判定，見上方；matter.js 現只用於落地散落。）
- **場景**：背景漸層 + 暖土色地面 + 接地陰影，脫離 unreal。所有東西(貓/包子/彈弓)貼地。
- **描邊標最新回覆**：最新吐出的包子有亮黃描邊(持久，下一顆吐出才轉移)，在散落堆積中一眼找到最新那顆。
- **射歪飛回彈弓**：射歪/沒命中的玩家包子飛回彈弓重瞄(保留輸入文字)。結構預留(returnToLaunch 獨立函式)，之後接貓尾巴。
- **點選/軌跡準確**：hit area 對齊視覺內容(非 sprite 整框)、半徑對應視覺大小。

關鍵架構決定：PixiJS ticker 統一驅動(不用 Matter.Runner)、混合架構(PixiJS canvas + HTML input)、canvas 寬度用 ResizeObserver(解 flex 佈局寬度時序)。

## ✅ 已完成:LLM 提前處理輸入 (latency 掩護)

把 submitAction 的 call 從「命中貓之後」提前到「按捏的瞬間」,結果暫存在那顆包子上,命中時直接取用——玩家「瞄準→射出→射歪飛回重射」的操作時間拿來掩護 LLM latency,餵到貓嘴回覆通常已備妥,貓幾乎不用等就吐。實玩驗過(含射歪重射、連發、秒回),順暢。

實作定案:
- 提前 call 在 `spawnBun`(按捏當下)發出,結果存 `bun.pendingResult: Promise<ActionResult> | null`。
- `busy` 從按捏(spawnBun)到 reply bun 落地全程鎖定 → 一次只有一個 call、輸入禁用、無並發 race。命中判定改用 `catPhase === 'idle'`(因 busy 提前設,不能再用 `!catBusy` 判命中)。
- 命中時 `Promise.all([bun.pendingResult, minDelay(MIN_CHEW_MS)])`:已備妥也保證最少嚼一段(MIN_CHEW_MS,檔案頂部常數,現 500,留給手感微調),避免秒回時貓沒嚼就吐的突兀。
- 射歪飛回重射復用同顆包子同 pendingResult(輸入沒變不重 call);error 由 rejected Promise 攜帶,走原有 catch fallback。
- 代價(已接受):提前 call resolve 後 world state 已更新,包子若在命中前被放棄則狀態已反映該動作。

## 📱 手機適配（2026-06-02）

web 版主要在桌面開發，這輪補手機（含 LINE 等 in-app browser）適配，踩到 iOS viewport 的坑。

### ✅ 已完成

- **旁白框改底部 sheet + 打字收起**：讀回覆的框（sheet）在桌面是置中 modal，手機（<640px）改成從底部冒出的 bottom sheet（maxHeight 45vh，不蓋住貓和包子）。**輸入框 focus（鍵盤要彈出）時收起 sheet**，blur 不自動彈回——打字和讀回覆是不同時刻，打字時不需要看舊旁白。
  - 教訓：原本想用 visualViewport 讓 sheet 跟著鍵盤定位，實機（LINE）不穩（iOS 鍵盤 viewport 跨環境行為不可靠），改「focus 收起」繞開整個坑。

- **整頁綁 visual viewport（解橫向溢出）**：iOS 鍵盤 / 系統 UI（靈動島、通話列）出現時壓縮 visual viewport（402→352），但內容（canvas/輸入列/chip/popup）寬度吃的是 layout viewport（402，不變）→ 內容超出可視區 → 整頁可左右滑、捏按鈕被切。修：JS 把 visualViewport.width 寫進 CSS 變數 `--vvw`，所有內容寬度綁 `min(原 maxWidth, var(--vvw))`，canvas margin 用 `--vvml` 修偏移，桌面 fallback 原樣。**canvas 全寬已達成。** 詳細根因/追蟲教訓見 BACKLOG F-mobile-viewport。
  - **跨裝置未驗**：只在 iPhone+LINE 驗過，其他裝置/in-app browser/橫向未驗，主動傳播前該驗一輪。

### 待做

- **手機 fit 一個畫面（縱向）**：手機直式下整頁可上下捲（canvas + chip + input 高度 > 可視高度），且 canvas 上方有空白（固定寬高比、上半是空天空）。要 fit 一個畫面、不上下捲。做法：收掉 canvas 上方無內容的空天空高度讓內容上移填滿（不變形、不動構圖、不丟內容），輸入列/chip 保留 padding。是高度版的「綁 visualViewport.height」，對稱於已完成的寬度版。見 BACKLOG F-mobile-fit。

## 🎯 操作分流設計

目標：減少 UX 負擔。不同操作各得其所，不是全部打字餵貓：

| 操作 | 怎麼做 | 狀態 |
|------|--------|------|
| 查看物品 | prefill 建議 → 點 → 餵貓 | ✅ 已做(chip);⚠️ 帶揭露缺陷,見下 |
| 移動/換房間 | 建築平面圖點地點(快捷鍵叫出 tap UI) | 下一個大方向 |
| 解謎/對話 | 捏包子餵貓 | 已做(核心爆點) |

解決最初痛點「全部打字餵貓太繁瑣」——高頻輕量的(查看/移動)簡化，核心好玩的(解謎/對話)保留餵貓儀式。

### ✅ 已完成:prefill 輸入建議 (chip 式)
依 engine 現有 sceneItems/exits/inventory 生成「查看{物品}」「前往{出口}」「使用{背包物品}」chip,空框閒置才顯示、一打字收起。chip **只填輸入框、不直接執行**(點了等同玩家打了那串字,仍要按捏餵貓)—— 刻意不做成 M2 那種「點了直接執行」的 tap UI,保住餵貓互動(viral 核心)。規則式、不用 LLM。每類數量上限 MAX_CHIPS_PER_CATEGORY(頂部常數)。跟 LLM 提前處理有綜效(產生輸入快 + 等回覆快)。

> **⚠️ 已知設計缺陷(查看 chip 提前揭露)**:「查看{物品}」chip 從 sceneItems 生成,而 engine **沒有 visibility 模型**——所有物件進房第一秒全可見,沒有「未發現」概念。所以像「桌上的便條」這種理論上要先查看桌子才該發現的物件,chip 會直接攤在玩家眼前,提前揭露、無法繞過(narration 的軟把關還可能含糊,chip 是白紙黑字列出)。這是 prefill **揪出**的既有 engine 結構缺陷(同「鎖門穿透」「孤兒物品」那族:LLM 軟性把關擋不住明確 UI)。chip 暫時留著,但 **engine visibility 模型(逐步揭露)已提為下一個動工項**(見 BACKLOG + 缺口分析),做好後查看 chip 改為依 visible 欄位過濾。
