# 分享卡 C 版：金句 + 滿地包子縮圖

> 狀態：**設計方向已定（C），尚未實作。** 前提 G-playable 已滿足（見設計文件 Gate）。
> 決定：分享卡一張兩層——**上半「這場的一句話」(金句)，下半「這場的現場」(本局滿地包子縮圖)**。一句話 + 一張現場圖，性質互補。

## 為什麼是 C
- 成功指標 = 值得分享。滿地包子(被埋的貓)是本遊戲最荒謬、最一眼看懂、最「你看我這場玩成什麼樣」的畫面，傳播力可能比純金句強。
- 金句卡(M4a)的 server 防偽 + 短碼是已投資好的資產，不丟。C = 保留金句 + 疊加現場圖，不是取代。

> **⚠️ 前提疑慮(待作者拍板,見 BACKLOG「Q-埋貓」)**:做手套移動包子時發現,現在的 3D 縱深架構下**包子圍不住貓**——貓在遠處深度平面,包子往那去會被透視縮小、且不在同一處,「被埋的貓」這個畫面實際長不出來。C 版整個立論建立在這畫面上,所以這是 C 版的前提性問題:若維持現架構,C 版的「現場感」可能要改用別的構圖(靠前地面一小堆 + 遠處的貓,而非埋住);若要真的埋住貓,得動空間架構(大改)。**做 C 版前要先確認這個。**

## 最關鍵待解：client 畫面 → server 卡
M4a 的卡是 **server 端生成**(從存的 scenarioTitle/quote/turnCount 畫成 OG 圖、不可偽造、`/s/{shareId}`)。
但「本局滿地包子」是 **client 端 PixiJS canvas** 的即時畫面，server 沒有它。

要解的就是這一步。**已定流程**(把 M4a 流程加一張圖,增量,不另起爐灶)：

1. 通關時**程式自動**截 canvas(滿地包子)→ **上傳** server(存圖,需 blob storage)。
2. **金句仍是 server 提供的選項**,client 端由玩家選一句(沿用 M4a 的選句)。
3. **server 統一合成**最終卡:把「上傳的滿地包子圖 + 選的金句」畫成一張卡(沿用 M4a 的 server 生成,只多畫一張圖進去)。
4. **預覽可能在 client 做**(合成前讓玩家看一眼)。
5. 成卡 → 分享(`/s/{shareId}`),維持貼連結社群自動展開預覽 + 防偽。

為什麼這條好:現場圖用 client 真截圖(不用 server 重畫,省事、真實);金句和最終合成都在 server(防偽、社群預覽都保住)。等於只在 M4a 既有流程上**多上傳一張圖**。

要標的小點(流程順序,不難):
- **截圖是程式自動**(通關觸發 canvas.toDataURL / render target 抓出),不需玩家手動。
- **預覽與 server 成品對齊**:若預覽在 client 拼,要讓它跟 server 最終合成長得夠像,不然「預覽 ≠ 實際分享出去的卡」。或改成 server 先回預覽圖。
- canvas 截圖要處理 devicePixelRatio / sprite / 字體。
- 截圖時機 = 通關當下(連到下方「夠不夠滿」問題)。

## 另一個現實問題：畫面夠不夠「滿」
滿地包子是**高互動量**的產物。普通場次玩家可能只丟五六顆就通關 → 畫面只有散幾顆、不荒謬、不值得分享。
- 要嘛只在包子夠多時才主推這張、少時 fallback 回純金句；
- 要嘛想辦法讓少包子時畫面也成立(例如把這局所有丟過的包子都畫進去，不只通關當下地上那些)。
→ 待定，但別忽略：不是每場都「滿」。
