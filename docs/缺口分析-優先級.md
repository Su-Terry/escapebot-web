# EscapeBot 缺口分析（兩軸並行 · 各自 Ship 線）

> **框架**：把優化拆成**兩條不互相排序的軸**——
> - **軸 A｜Viral（吸引 / 傳播）**：讓玩家進來、想分享。北極星「值得分享」。
> - **軸 B｜流失（留得住）**：別讓玩家因設計不良走掉。標準「有多少玩家因謎題設計不良流失」。
>
> 兩軸衡量**不同面向**，不放同一隊列比誰前誰後。這化解「賣貓還是賣密室」的偽二選一——**不選**：貓/互動負責 viral，謎題負責不流失，各自達標即可。
> 兩軸**各有 ship 閘門，兩個都過才丟玩家**。判斷用直覺，不是檢查表。

## 軸 A｜Viral（吸引 / 傳播）
> **Ship 閘門（直覺）：玩完，你自己會不會想把某個東西傳給朋友？講不講得出一句「我剛剛……」。** 講不出 = 還沒到。

分兩種爆點，**時間差不同**：

### A1 互動爆點（「第一次看到就想傳」）— 其實已做好，要當資產看
- 捏包子 → 彈弓 → 貓吃 → 貓吐 這條鏈。「我把一句話捏成包子射給貓」本身就夠怪、第一次看到就想傳。
- EscapeBot 最獨特的是**互動方式**，不是 AI 生成的內容（interaction-first，像 Wordle 傳格子不傳答案）。
- **已完成**（M3 + 3D）。缺的是**意識到它是最強 viral 資產、去放大它**（分享時把這個互動本身講出來，而不只給張結果卡）。
- 槓桿：高 ｜ 成本：低（已做，差包裝）。

### A2 內容爆點（「玩久了才想傳」）
- **貓人格**：可轉述句子的來源。聲音方向**待你定**——「認真但奇怪」(世界觀人格：貓真的相信自己在跟門溝通，「我向門轉達了你的請求，門拒絕回應」) 看來比純毒舌好（不搶戲、不破壞解謎節奏、不跟修2 打架）；但這是你的創作決定。牽 engine（system prompt persona + 與修2 協調，毒舌到把線索講錯會破壞可解性）。
- **weird / 黃金 / 腐爛包**：截圖理由。與貓人格一體（腐爛包配一句台詞 = 一個完整事件）。牽「誰標類型」→ engine。
- 槓桿：高 ｜ 成本：中。

### A3 內容供應 / 第二次分享
- **Replay（重玩）**：程序生成產品鐵律——每次不同 → 重玩不是附加功能，是**內容來源**（Roguelike / AI Dungeon 同理）。沒 replay = 沒第二次故事 = 沒第二次分享。**提前到與 A2 同級**（原本低估）。
- **滿地包子卡 / 金句卡**：分享物（滿地卡依賴生成修好）。
- 槓桿：中高 ｜ 成本：中（replay 已有 spec）。

### A4 場景辨識度（不是美術 polish）
- 「我剛剛在貓的大腦裡解謎」可傳；「研究室背景比較精緻」不可傳。**辨識度是內容、不是 polish。**
- 牽 **generator**：要生成有強 identity 的怪地點（貓的腦袋 / 鯨魚肚子 / 壞掉的販賣機），不是事後貼背景圖。連動「謎題多樣性」（同一個 generator 創意源頭）。
- 槓桿：中高 ｜ 成本：中（牽 generator）｜ **需料**：你 generator 現在產出的場景有沒有 identity，我沒看過樣本。

## 軸 B｜流失（留得住）
> **Ship 閘門（直覺）：有沒有玩家會因為謎題/體驗爛到想關掉？** 衡量**流失嚴重度**，不是「可解性百分比」。偶爾不可解、玩家聳肩重開（尤其有 replay）= 可接受；爛到「覺得這遊戲在唬爛」再也不回 = 致命，要修。

### B1 謎題合理性 / 可解性（用流失衡量，不追求 100% 可解）
- generator 設 solution 但不驗證「線索能否推出答案」。一批 bug：F-spoil、容器鎖、重複 item、位數不符、鑰匙語意。
- 尺：**修到「不會讓人想關掉」**，不是完美。致命流失的先修，沒到的晚修。
- 早期用直覺（這謎題爛到會讓人走嗎）；有玩家後看實際流失到第幾關。
- 徹底解 = Phase 3 因果圖（護城河，不擠現在；長期也是未來付費 host 的「可解性保證工具」——見設計文件長期方向）。

### B2 遊戲理解（懂不懂這是解謎）
- 可愛蓋過「這是密室逃脫、要解謎逃出」→ 玩家以為是餵貓玩具 → 玩兩下走掉。
- **需料**：新玩家實際反應。連動 A1（互動懂了，但「有謎題要解、有目標」這層懂沒）。

### B3 prefill 輸入建議 — ✅ 已完成(帶缺陷,見 B0)
- 空輸入框不知道打什麼 → friction → 流失。規則式 chip「查看X/前往Y/使用Z」(不用 LLM)。chip 只填框不執行、空框才顯示、一打字收起。已完成。
- ⚠️ **查看 chip 提前揭露**:見下方 B0(prefill 揪出的 engine 缺陷)。

### B0 (next up,最高優先) engine visibility 模型 / 逐步揭露
- **缺陷**:engine 沒有「物件被發現了沒」的概念——所有物件進房第一秒全可見、全可 take。「查看桌子才發現便條」這層探索**從來不存在**,只靠 turnHandler prompt 軟性求 LLM 別說漏嘴。prefill 的查看 chip 把這個缺陷無法繞過地攤出來(明確列出「查看便條」)。
- **同族**:跟「鎖門穿透」「孤兒物品」同一個教訓——LLM 軟性把關擋不住明確 UI / state 缺欄位。該補的是 state 結構(Item 加 hidden/revealedByAction、「查看」變成會 promote 物件的真動作、toView 與 LLM context 依 visibility 篩)。
- **不只是修 bug**:它是「逐步發現/探索層次」這個遊戲性的基礎(目前完全沒有)。架構級,動手前說明方向。
- **優先級**:作者拍板提到軸 B 最前、**下一個動工**(非 T0 阻斷——遊戲照玩、能通關、能驗證,只是探索被提前揭露;但不讓它無限期靠軟把關撐著)。做好後 prefill 查看 chip 改依 visible 過濾。

### B4 QoL（較輕的流失 / 體驗）
- 撿包子整理收藏（多了找不到要讀的那顆）、貓動畫 frames（placeholder→咬嚼吐，反應豐富也減「假」感）、hover 提示（待確認）。
- 美術一致性 polish：低（與 A4 辨識度不同，這只是精緻度）。

### B5 修2 驗證（低成本）
提示限遊戲內資訊已 ship，待新場景多玩幾場驗 nonsense 有沒有減少。
